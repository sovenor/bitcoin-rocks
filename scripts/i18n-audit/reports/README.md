# i18n-audit / reports

Per-language translation work queues generated by `language-diff.js` and
consumed by `apply-translations.js`. See
`.clinerules/workflows/translate-v2-refresh.md` for the full workflow.

## Layout

```
reports/
├── README.md            (this file)
├── <lang>.json          (live report — translator fills in targetTranslation fields)
└── applied/             (archived reports after successful apply runs)
    └── <lang>-<UTC-timestamp>.json
```

Typical report is ~200–250 KB (one object per entry flagged for
translation, with English source + current target value + null
placeholder for the translated value).

## Entry `reason` categories

Every flagged entry has one of four `reason` values, evaluated in
priority order:

| Reason | Meaning |
|--------|---------|
| `missing` | Key is in English but absent from the target file. Translator must add + translate. |
| `untranslated` | Target value is byte-identical to English. Usually a placeholder the translator forgot to fill. Exempts brand names / URLs / numeric tokens. |
| `english-changed` | **Strong stale signal.** English was rewritten since the frozen pre-V2 baseline (`../english-snapshot-preV2.json`) AND the target translation reflects the old wording. Entry includes both `englishValue` (current) and `englishValueBefore` (pre-V2) so the translator can see the rewrite. Skips files whose `@metadata.last-updated` is already >= English's (the "freshness gate"). |
| `likely-stale` | Heuristic. Weak backup signal based on V2-era markers like "Source:" / "What's next". Demoted below `english-changed`; disable with `--no-flag-likely-stale`. |

See `.clinerules/workflows/v2-translate-refresh.md` § "Pre-V2 baseline"
for why `english-changed` exists.


## Lifecycle

1. `node scripts/i18n-audit/language-diff.js <lang>` → writes `<lang>.json`.
2. Translator fills in every `"targetTranslation": null` field with the
   native-language value (directly in the JSON, or via per-category
   helper scripts in `scripts/<lang>-v2-refresh/` — the split-by-category
   pattern from `.clinerules/workflows/translate-new-language.md`
   applies the same way here).
3. `node scripts/i18n-audit/apply-translations.js <lang>` → merges every
   resolved entry into the `i18n/<lang>/**/*.json` tree, bumps
   `@metadata.last-updated`, and archives the report to
   `reports/applied/<lang>-<timestamp>.json` (live report deleted).

If a session runs out of context or time partway through translating,
run `apply-translations.js --partial` to flush what's done — the script
will retain unresolved entries in `<lang>.json` for the next session to
continue.

## Are the live reports committed?

Yes. Reports are tracked in git so contributors can pick up a
translation mid-stream, review progress across sessions, and resume
across machines. Archived reports in `applied/` are also committed as
an audit trail.
